## Verified baseline-runtime finding

Before the implementation milestone, there was **no rendered application to map**: `package.json` had no `dev`, `start`, or `build` script, and the repository had no Next/Vite/static web entry point, pages, route handlers, browser assets, or frontend components. Consequently no browser server could be started from the baseline checkout, and there were no existing URLs, modals, breakpoints, or visual states to inspect.

The only executable baseline surface was the TypeScript/domain/database test suite. It was run on 2026-09-09: **127/127 tests passed** against the existing foundations, including real PostgreSQL security and posting tests. This verified the Stage 0 ledger/auth foundation, not a user interface.

All `Current` entries below describe that baseline and therefore mean **not implemented**, rather than an inferred UI defect. No application source was changed during the mapping phase.

## First implementation checkpoint

The safe UI foundation has progressed beyond the original checkpoint. The latest vertical slice adds an owner-only closed-day purchase cost-correction route, value-only immutable ledger record and owner read-model display, alongside the earlier opening/adjustment, inventory drill-down and pending-sale correction work. Service/API tests use real PostgreSQL and PGlite migration tests verify the ledger shape; static rendering verifies the owner/operator initial UI boundary. These do not verify a signed-in journey or visual layout. A browser binary and configured non-production Supabase project are still unavailable in this sandbox, so viewport/zoom/keyboard inspection and provider sign-in remain `BLOCKED BY OWNER OR EXTERNAL ACTION`.

## Role and navigation boundary

| Role / state | Intended landing surface | Navigation boundary |
|---|---|---|
| Unauthenticated owner or operator | `/login` | May only access authentication, privacy notice, session-expired and offline help surfaces. |
| First-run owner | `/setup` | Setup is reachable only until a yard is configured; it must not expose a partially configured operational shell. |
| Owner | `/today` | Can reach every yard-operational route except platform administration. Financial values, history, private buyer terms, corrections, export and settings remain owner-only. |
| Operator / scale staff | `/today` | Sees only two fast operational actions and own-current-day entries. Cannot reach cost, profit, cash total, all-history, directory/private relationship, users, settings, reports, regrade, adjustments or reversals. Server authorization remains authoritative. |
| Platform administrator | `/admin/directory` | Separate non-yard surface for central-directory curation only. It must never appear in yard navigation or gain ledger access. |

## Global state contract for every route

| State | Required presentation and recovery |
|---|---|
| Initial loading | Preserve header/shell; use a content-shaped skeleton with an Arabic accessible status. Never show fabricated zero financial values. |
| Refreshing / partial data | Keep last verified data visible with “last updated” context; disable only actions whose fresh data is required. |
| Empty first use | State the next operational outcome and give one safe primary action (for example “أضف أول صنف” or “سجّل أول شراء”), not a decorative illustration alone. |
| No results | Preserve filters/search query, explain that no matching records exist, and offer “clear filters” where applicable. |
| Recoverable validation error | Keep all user input and focus the summary/first invalid field; the server message must explain both cause and valid path forward. |
| Mutation success | Give an explicit, accessible confirmation with the record number/status and next safe action. Avoid blocking toast-only receipts. |
| Offline / interrupted save | State whether a draft is local, whether a request is retrying, and its idempotency-safe pending state. Never show it as posted before server confirmation. |
| Permission denied | Explain that the account cannot perform the action without naming hidden records or values; offer a return route. |
| Expired session | Preserve non-sensitive draft locally, clear session-bound caches, then return to login with a clear continuation path. |
| Disabled action | Keep the reason adjacent to the control; for stock, name material/available/shortfall and the permitted recovery. |
| Error / not found | Use a route-safe error page; distinguish unavailable service from a record that cannot be viewed only when doing so does not leak protected data. |
