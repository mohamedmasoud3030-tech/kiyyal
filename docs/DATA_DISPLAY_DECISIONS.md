# Data Display Decisions

**Decision status:** architecture defined. The implemented data-bearing subset is `IMPLEMENTED BUT NOT VERIFIED` pending authenticated browser viewport evidence; unlisted decision rows remain `NOT STARTED`.
**Principle:** representation follows the user’s decision/task—not the database table or a generic dashboard pattern. All owner-only financial fields are omitted at the API boundary for operators before a pattern receives data.

## Cross-product pattern rules

| Rule | Decision |
|---|---|
| Charts | **No chart is selected for MVP.** The owner needs current totals, a filtered period result and traceable rows; trend charts do not improve a stated decision and would add visual/technical cost. A future trend chart requires a documented decision question and accessible table equivalent. |
| Financial record selection | No bulk selection/bulk edit/bulk delete for transactions, cash movements, stock, party ledger or regrades. Every correction is record-level, state-aware and auditable. |
| Desktop table / mobile strategy | Do not shrink a comparison table. At phone width, inventory, material catalog, party register, history and report tables transform into summary cards/list rows with a drill-down. At tablet width, only essential columns stay in a contained horizontal table when comparison is necessary. |
| Pagination | Transaction history uses server-side keyset pagination with stable sort keys and explicit previous/next controls; it deliberately returns no total count, avoiding an expensive ledger-wide scan or disclosure about inaccessible rows. Reports use the same cursor direction when implemented. No infinite scroll that hides an audit boundary. Today surfaces a bounded recent list plus “view all.” |
| Search | Server-side bounded search for large or protected collections; History applies it on an explicit form submission to avoid a request per keystroke. Persisting query state in the URL remains planned. Fast transaction pickers may search cached, scoped reference data first then query the server. |
| Status vocabulary | Use explicit, text-bearing status badges—not colour alone—for posted/pending tare/pending stock/reversed/voided, active/inactive, directory active/unverified/outdated, session locked/active, connection/retrying/offline and allocation deferred/resolved. |
| Dates/numbers | Arabic RTL layout, Western numerals by default, strings from the API for money/weight, `DD/MM/YYYY` Cairo time. Values are formatted by a display-only formatter; UI never reuses formatted strings for calculations. |
| Keyboard/screen reader | Tables use semantic `<table>` only when rows/columns are genuinely comparable. Sort controls announce sort direction; filters have labels and result counts; expandable cards use `<button aria-expanded>`; status is textual; pagination exposes current page; menus return focus to trigger. |
| Loading and partial data | Skeleton shape matches final pattern. Keep verified prior data during refresh with freshness label. Never fill an unavailable financial value with zero. |
| Empty/no results | Empty first-use state gives one primary safe action; no-results retains filters/search and offers reset. Distinguish “no data yet” from “not authorized” and “service unavailable.” |

## Pattern implementation safeguards

1. `DataTable` receives data already scoped and shaped for the viewer. It never conditionally hides a sensitive column from a broad object.
2. Every mobile card has a visible label for every financial value; a value is never inferred from spatial position alone.
3. Every filter reset and pagination transition retains focus/announces the new result set without resetting scroll unexpectedly.
4. Actions are not buried behind hover-only controls. On touch, a labelled action menu/sheet is used; on desktop, menu items are keyboard reachable.
5. Empty state text distinguishes no records, no match, unknown/offline and no permission. It never suggests “add” when the role cannot add.
6. The chosen patterns will be evaluated with Arabic names exceeding 60 characters, long governorate/material combinations, a 200% browser zoom and a 320px viewport before each route earns `VERIFIED COMPLETE`.
